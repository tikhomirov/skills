# Recipe: Core Library Extraction (Чистое доменное ядро)

## Паттерн из практики
Основан на архитектурном разделении **`woo2iiko`** и **`iiko-core`**.

## Проблема
Когда плагин интеграции (с CRM, ERP, банком, службой доставки) пишется как единый WP-монолит, логика протокола, парсинга DTO и транспортный уровень переплетаются с хуками WordPress (`add_action`, `wp_remote_post`, `$wpdb`). Это делает код нетестируемым без базы данных и исключает его переиспользование в CLI, микросервисах или других CMS/фреймворках (например, Laravel).

---

## Решение: Выделенная автономная библиотека
Домен и транспорт выносятся в отдельный Composer-пакет с нулевыми зависимостями от WordPress:

```text
my-integration-core/             # Автономный Composer пакет (чистый PHP 8.3+)
├── composer.json                # Зависимости: Guzzle/Symfony HttpClient, Webmozart Assert
├── src/
│   ├── Client/                  # HTTP транспорт, работа с токенами, ретраи
│   ├── DTO/                     # Неизменяемые Data Transfer Objects
│   ├── Exceptions/              # Доменные исключения
│   └── Services/                # Чистая бизнес-логика (расчет сумм, валидация)
└── tests/                       # Быстрые PHPUnit / Pest тесты (100% покрытие за секунды)
```

### Плагин-адаптер (`wp-integration-plugin`):
Подключает core-библиотеку через Composer и занимается **только адаптацией под WordPress**:
- Маппинг сущностей `WC_Order` / `WP_Post` в чистые DTO библиотеки.
- Подписка на хуки WooCommerce / WordPress.
- Сохранение статусов в базу через `OptionRepository` или кастомные таблицы.
- Отправка фоновых задач через `wp-queue`.

---

## Плохие знаки
- Внутри класса HTTP-клиента вызывается `get_option()` или `update_post_meta()`.
- Доменные сущности зависят от глобального класса `$wpdb`.

## Хорошие знаки
- Core-пакет может быть установлен в чистый CLI-скрипт или Laravel-проект.
- Модульные тесты ядра выполняются без моков ядра WordPress.
