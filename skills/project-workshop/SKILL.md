# Project Workshop — настройка проекта с человеком

Это отдельный скилл комплекса obsidian-project-framework, не расширение ai-docs-setup. Технические форматы описывает obsidian; рабочую механику — obsidian-project-framework.

## Порядок
1. Прочитать существующие AGENTS, _statuses, карту, правила репозитория и решения. Не заменять существующие договорённости своими предположениями.
2. Выяснить цель проекта и границы, затем состав/названия/расположение модулей, правила доступа и публикации, статусы и критерии готовности, порядок архивации. Задавать по одному небольшому блоку вопросов, а не огромную анкету.
3. Показывать короткое предлагаемое содержание и точные пути. Различать подтверждение концепции и разрешение изменить конкретные документы. До ответа черновики держать только в _agents/Knowledge/Proposals/.
4. После подтверждения записать согласованные AGENTS.md, компактный _statuses.md, карту и явно разрешённую документацию модулей. Не создавать HUMAN/. Не заполнять неизвестные факты вымыслом.
5. Ключевые решения пользователя добавлять событиями в Решения/ с источником, датой и id задачи; исправление — новое событие, не переписывание истории.
6. _statuses.md держать минимальным: заголовок и таблица status/Название/Роль/Описание. Общие правила и примеры туда не добавлять — агент читает файл постоянно. Подробные правила — в скилле/AGENTS.
7. Проверить ссылки, YAML, доску и сохранность старых материалов; показать пользователю что создано и что осталось неподтверждённым.

## Обязательные договорённости
- Действие человека на доске приоритетнее имени файла, тега и памяти. Перед работой task sync; не откатывать перенос человека.
- Пометка Done пользователем — не доказательство тестов. Сохранить статус, отдельно отметить отсутствие/устаревание проверки. Для завершения самим агентом отчёт и проверки обязательны.
- Архив только по явной команде: Tasks/_archive/<год> с таблицей _Архив.base и текстовым _INDEX.md. Активный Tasks/_INDEX.md не нужен.
- Подтверждение модулей не означает разрешение редактировать их документацию впредь.
- Применять improvement до и после изменения: ограничить диапазон, проверить соседние контракты, подготовить откат для живой базы.
