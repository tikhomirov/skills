# Obsidian Project Framework

**obsidian-project-framework — комплексное решение**, объединяющее скиллы, проектные инструкции, шаблоны и исполняемые CLI-файлы. Этот SKILL.md — входная инструкция для агента, а не всё решение целиком.

Состав: технический скилл obsidian; этот скилл и рецепты рабочего протокола; генерируемые AGENTS.md и _statuses.md; шаблоны и структура базы; исполняемая команда obsidian-project-framework. Компоненты должны следовать одним правилам и обновляться согласованно.

## Ответственность
- **obsidian** — точные инструкции по инструментам и форматам Obsidian: Markdown, Properties/YAML, wiki-ссылки, Bases, Canvas, CLI приложения.
- **obsidian-project-framework** — структура проекта, границы записи, задачи, решения, память и отчётность.
- **CLI obsidian-project-framework** — вспомогательные скрипты для соблюдения протокола. Без них агент выполняет те же действия вручную. Скрипты работают с файлами без запущенного Obsidian; это не CLI приложения `obsidian`.

## Структура

```text
<Vault>/Projects/<project>/
├── AGENTS.md                     # Правила, краткая архитектура, указатели
├── _statuses.md                  # Источник статусов задач, описаний и порядка колонок
├── _шаблоны/                     # Сообщения по модулям, карточки и документы
├── _вложения/
├── _служебное/                   # Проектные скрипты и генераторы
├── Tasks/                        # Существующая Задачи/ также поддерживается
│   ├── _INDEX.md                 # Задача + описание + статус + дата
│   ├── _Задачи.base              # Нативная канбан-доска Obsidian 1.14+
│   └── TASK-001_backlog_2026-10-27.md
├── Решения/                      # Только добавление: история решений пользователя
├── 01_НазваниеМодуля/            # Пример согласованной пользователем документации
├── 02_ДругойМодуль/              # Число модулей < 10: допустимы модули в корне
└── _agents/                      # Служебная рабочая зона агента
    ├── Memory/
    │   ├── NOW.md
    │   ├── STATE.md
    │   └── sessions/
    ├── Knowledge/
    │   ├── _INDEX.md
    │   ├── Карта проекта.md
    │   └── Решения — таймлайн.md
    └── Reports/
```

Существующий `Проекты/` равноправен `Projects/`; не создавать параллельную базу из-за языка имени.

### Модули определяет пользователь
1. Исследовать текущую структуру и перечислить найденные компоненты **как предложение**, а не как утверждённые модули.
2. Спросить пользователя: «Подтверждаешь состав, названия и расположение модулей: …?» Если структура ещё не определена — попросить назвать модули.
3. Дождаться ответа. Не создавать модули автоматически. Утверждение списка не равно разрешению написать/переписать документацию.
4. При числе менее 10 допустимы корневые `01_Имя/`, `02_Имя/`. Другой вариант — `Модули/<Имя>/`; при 10 и более предложить его и также подтвердить. Не перестраивать существующее расположение без просьбы.
5. **API — возможный модуль приложения**, а не обязательная папка фреймворка. Название и место API подтверждаются вместе с остальными модулями.
6. После подтверждения записать решение пользователя в Решения/, а карту со ссылками — в `_agents/Knowledge/Карта проекта.md`.

### Границы записи
| Раздел | Что разрешено |
|---|---|
| `_agents/` | Свободно вести рабочие материалы агента. Memory, Knowledge, Reports — базовые каталоги; дополнительные папки и ссылки на скиллы допустимы по необходимости. |
| `Tasks/` (или существующая `Задачи/`) | Создавать и вести карточки, обновлять статусы, ссылки и генерируемый индекс. |
| `Решения/` | Только добавлять новые события о решениях пользователя. Читать можно; изменять, переименовывать и удалять прошлые записи нельзя. |
| Пользовательские модули, включая `Модули/`, `01_…/` | Только читать. Создавать или менять документацию — исключительно по явной просьбе пользователя о такой правке. |
| Корневые AGENTS/архитектура | Читать как правила; существующее содержимое менять только по явной просьбе. Инициализация создаёт отсутствующий AGENTS, но не перезаписывает его. |

Общее поручение изменить код, автоматический `knowledge sync` или смена статуса задачи **не разрешают** менять документацию модулей. После изменения кода записать выводы и предложенные правки в `_agents/Knowledge/` и Reports; при необходимости запросить разрешение. При переименовании карточек скрипты не переписывают модули и историю решений.

### Решения — история, а не редактируемая справка
- Записывать ключевые решения **пользователя**, а не гипотезы/предложения агента.
- Каждое событие: стабильный id, содержание, дата, источник подтверждения, `task_ids`, при необходимости связь `supersedes` с прежним решением. Для более раннего решения передать `--decided-at YYYY-MM-DD`; recorded_at сохраняет время записи отдельно. Без флага записывается текущее событие. Не выдавать время записи за неизвестную дату согласования.
- Отмена, уточнение, исправление или замена решения — **новая запись**, ссылающаяся на прежнюю. Оригинал остаётся неизменным.
- Строить граф через wiki-ссылки между решениями; основной хронологический обзор — генерируемый `_agents/Knowledge/Решения — таймлайн.md`, со ссылками на решения и актуальные карточки задач.
- В неизменяемом событии хранить стабильные id задач, а не ссылки на меняющиеся имена карточек. Таймлайн обновляется в рабочей зоне, не в Решения/.
- Источник решения обязателен. Нельзя самому «согласовать» решение от имени пользователя.

### `_statuses.md` — пользовательский источник статусов
Файл создаётся в корне проекта командой init. Агент **обязан прочитать его перед созданием задачи, выбором/сменой статуса и синхронизацией доски**. Нельзя использовать жёстко заданный список из скилла, шаблона или памяти вместо этого файла.
Пользователь вправе расширять, переименовывать и менять статусы, их описания и порядок. Агент изменяет реестр только по явной просьбе пользователя. Если пользователь попросил изменить статусы, а файла ещё нет — создать его в корне, согласовать описание и перенести туда определения.
Формат — таблица status / Название / Роль / Описание. Идентификаторы используются в карточках, именах и тегах; порядок строк — порядок колонок. Роли backlog/active/done задают поведение команд и требования к готовности; **это не запрет на дополнительные статусы**. Например review и blocked могут иметь роль active. Для каждой роли нужна хотя бы одна строка; первый backlog используется при create, первый active — при start, первый done — при complete.
После изменения реестра выполнить task sync. При удалении/переименовании сначала добавить новые значения, явно сопоставить существующие задачи, перевести их, затем убрать старые строки и снова синхронизировать. Не скрывать карточки с неизвестными статусами и не подменять реестр встроенными значениями. Подробности — [statuses](recipes/statuses.md).

### `_Задачи.base` — канбан-доска Obsidian
Это **настоящая встроенная канбан-доска**, не таблица и не обычный вид Cards. Создаётся по умолчанию командой init. Требуется **Obsidian 1.14+** с включённым Bases; сторонний Kanban-плагин не нужен.
Доска выбирает все карточки type: task из текущей папки Tasks/ (или существующей Задачи/), группирует по редактируемому note.status и берёт groupOrder из _statuses.md. Начальные колонки:
1. **Backlog** — backlog.
2. **In Progress / В работе** — in-progress.
3. **Done / Завершено** — done.
Это начальная конфигурация, не фиксированный набор. После настройки использовать только значения и порядок из _statuses.md. Заголовки колонок соответствуют значениям status. groupOrder скрывает другие значения, поэтому неизвестные статусы требуют явного согласования; init и doctor сообщают о проблеме.
В Obsidian открыть _Задачи.base: карточки используют title, summary, id, tags. Все данные остаются в Markdown-карточках; _INDEX.md — дополнительный текстовый индекс.
**После перетаскивания карточек выполнить `obsidian-project-framework task sync`:** Obsidian меняет только status, а скрипт идемпотентно согласует имена, даты, теги, ссылки, индекс и память. Не требуется запускать watcher. До переноса в статус с ролью done должны быть записаны отчёт и успешные проверки; иначе синхронизация сообщит о незавершённой задаче. Для атомарной смены использовать task start/status/complete.
Точный синтаксис и ограничения нативного Kanban — в скилле obsidian.

## Протокол работы
1. Прочитать AGENTS репозитория и базы; затем `_agents/Memory/NOW.md`, индекс и карточку задачи.
2. Проверить статус, критерии готовности, связанные задачи и зависимости. Читать только нужные модули, решения и знания.
3. Один факт — один источник: код описывает поведение, решения пользователя — требования. Расхождение показать пользователю.
4. У задачи обязательны описание/summary, `id`, `status`, `status_changed`, даты, `tags`, `related`, `depends_on`, `sources`, критерии готовности и результат.
5. Имя: `TASK-NNN_<status>_<YYYY-MM-DD>.md`; дата — смена статуса в UTC. Теги: `задачи`, `статус/<status>`, дополнительные предметные теги по необходимости.
6. Статус меняется вместе с именем, датой, тегом, индексом и памятью. Точные ссылки исправлять только в разрешённой рабочей зоне; защищённые документы не трогать. Для неизменяемых записей использовать стабильный id и таймлайн.
7. Отчёт `_agents/Reports/TASK-NNN.md`: что сделано, реальные проверки, Git, источники, ограничения, какие изменения модульной документации предложены и разрешены ли они. Не отмечать проваленные/непроведённые проверки как passed.
8. Допустимые статусы и их смысл определены только в _statuses.md. Начальный поток backlog → in-progress → done можно расширять по просьбе пользователя. Перед стартом проверить зависимости; перед ролью done — отчёт и проверки. Возврат из завершения в работу сбрасывает готовность старого отчёта.
9. NOW — короткий фокус; STATE — сводка; sessions — передача контекста. Карта проекта и исследования — в Knowledge; процедурные скиллы не превращать в дублирующие проектные знания.
10. Повтор команд с теми же данными при том же состоянии — no-op без дублей, смены дат и переписывания неизменившихся файлов. `task create` использует `--key`, по умолчанию точное название. `--dry-run` не создаёт даже каталоги.
11. Не копировать секреты, не обходить границы проекта симлинками, не удалять источники при миграции. Коммиты, публикация и стенды — только по явным правилам текущего проекта.

## Рецепты и скрипты
| Операция | Рецепт | Команда |
|---|---|---|
| Инициализация без создания модулей | [init](recipes/init.md) | `obsidian-project-framework init` |
| Пользовательские статусы и порядок колонок | [statuses](recipes/statuses.md) | `_statuses.md`, затем `task sync` |
| Канбан, карточки и синхронизация после drag-and-drop | [tasks](recipes/tasks.md) | `obsidian-project-framework task …` / `task sync` |
| Новое решение пользователя | [decisions](recipes/decisions.md) | `obsidian-project-framework decision record …` |
| Память между сессиями | [memory](recipes/memory.md) | `obsidian-project-framework checkpoint` |
| Контекст и карта проекта | [context](recipes/context.md) | `obsidian-project-framework context` |
| Поиск | [knowledge](recipes/knowledge.md) | `obsidian-project-framework knowledge search` |
| Отчёт и рабочие знания | [knowledge-sync](recipes/knowledge-sync.md) | `obsidian-project-framework knowledge sync` |
| Неразрушающий импорт | [migrate](recipes/migrate.md) | `obsidian-project-framework migrate` |
| Проверка структуры | [doctor](recipes/doctor.md) | `obsidian-project-framework doctor` |

Каждая команда поддерживает `--help`. Vault: `--vault`/`OBSIDIAN_VAULT`; проект: `--project`/`.project-id`.
