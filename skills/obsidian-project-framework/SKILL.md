# Obsidian Project Framework

Комплексное решение, не только скилл. `obsidian` описывает инструменты/форматы; этот скилл — процесс; `project-workshop` — диалоговую настройку. CLI `obsidian-project-framework` помогает соблюдать процесс и работает без запущенного Obsidian. Без CLI выполнять тот же протокол вручную.

## Структура проекта
```text
Projects/<id>/                 # Существующая Проекты/ равноправна
  AGENTS.md                    # Правила, краткая архитектура, указатели
  _statuses.md                 # Только заголовок и таблица статусов
  _шаблоны/                    # Шаблоны документов и сообщений по компонентам
  _вложения/
  _служебное/
  Tasks/                       # Существующая Задачи/ поддерживается, не дублировать
    _Задачи.base                # Нативный Kanban Obsidian 1.14+
    TASK-001_backlog_2026-10-27.md
    _archive/<год>/            # Архивные карточки
    _archive/_Архив.base       # Табличная БД архива
    _archive/_INDEX.md         # Индекс только архива
  Решения/                     # Неизменяемая история решений пользователя
  _agents/
    Memory/                    # NOW.md, STATE.md, sessions/
    Knowledge/                 # Карта проекта, исследования, Proposals/, таймлайн
    Reports/                   # Результаты и фактические проверки
```

Модули задаёт пользователь: спросить состав, названия и расположение, дождаться подтверждения. При числе менее 10 допустимы `01_Имя/` в корне; другой вариант — `Модули/<Имя>/`. API — возможный модуль, не обязательный раздел. Init модули не создаёт.

## Права
- `_agents/`: свободная рабочая зона; дополнительные материалы и указатели на скиллы допустимы. Активные скиллы устанавливать штатным установщиком.
- `Tasks/`: вести карточки и доску. Активного `_INDEX.md` нет.
- `Решения/`: читать и добавлять подтверждённые события; не менять, переименовывать и удалять прошлое. Исправление — новая запись с `supersedes`.
- Документация модулей, существующие AGENTS/Архитектура: читать; писать только по явной просьбе о соответствующей правке. Подтверждение списка модулей и поручение изменить код такого права не дают.

## Перед работой
1. Прочитать AGENTS репозитория и базы, `_statuses.md`, NOW и нужные карточки. Затем только релевантные источники.
2. Выполнить `task sync`: сохранённый `status` с доски приоритетнее имени файла, тегов и памяти. Не откатывать действия человека.
3. Код описывает фактическое поведение; решения пользователя — требования. Конфликт показать пользователю, не подменять одно другим.
4. Применять `improvement` до и после правок: проверить пользу, простоту, диапазон и влияние на соседние контракты.

## Задачи и канбан
- Данные — Markdown-карточки, `.base` — представление. Обязательны id, title, summary, status, status_changed, created/updated, tags, related, depends_on, sources, критерии готовности и результат.
- Имя `TASK-NNN_<status>_<YYYY-MM-DD>.md`; дата UTC — смена статуса, не правка текста. Теги: `задачи`, `статус/<status>`.
- `_statuses.md` — единственный источник значений/ролей и порядка колонок. Начально backlog → in-progress → done. Пользователь может расширить список; агент — только по его просьбе. Файл держать минимальным, читать перед операциями с задачами.
- Роли backlog/active/done определяют create/start/complete; необязательная роль archive — завершённая карточка для архива; число пользовательских статусов не ограничено. Неизвестные значения не преобразовывать по догадке.
- Нативный Kanban требует Obsidian 1.14+ и Bases. Перенос меняет status, но не имя/теги; `task sync` согласует производные данные. Дата sync — время обнаружения, не доказанное время переноса.
- Done с доски сохранять даже без отчёта, помечая `verification_state: user-marked-review-required`. Это не доказательство проверок. Агент через complete обязан предоставить актуальный отчёт. Повторное открытие сбрасывает готовность прежнего отчёта.
- Исправлять ссылки только в разрешённой зоне. В неизменяемых решениях хранить стабильные task_ids; текущие ссылки — в рабочем таймлайне.
- Архив только по явной команде, только завершённые задачи (роль done или archive); при наличии роли archive карточка получает этот статус, restore возвращает первый статус done; восстановление сохраняет ID. Активная доска исключает archived; ID не переиспользуются.

## Результат и безопасность
- В Knowledge записать проверенные выводы/sources; в Reports — результат, реальные проверки, ограничения и предложенные правки модулей. Не выдумывать согласование или успех тестов.
- NOW — короткий фокус; STATE — сводка; sessions — передача контекста. Один факт — один источник, в других местах ссылка.
- Решение пользователя: содержание, источник, дата, task_ids, при необходимости supersedes. Таймлайн генерируется в Knowledge, не в истории решений.
- Повтор команд с теми же данными/состоянием — no-op. Create использует --key, по умолчанию название; новая одноимённая задача требует другого ключа. Dry-run не пишет даже каталоги.
- Не копировать секреты, не выходить через симлинки за границы проекта. Миграция — с резервной копией, без удаления исходников. Коммиты/push/публикация — только по разрешению.
