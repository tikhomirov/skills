# Задачи и нативная канбан-доска Obsidian

## Доска
`Tasks/_Задачи.base` — **встроенный Kanban Obsidian 1.14+**, создаётся init по умолчанию. Если проект уже использует Задачи/, доска и карточки остаются там; вторую папку не создавать. Это не таблица, не обычный Cards и не Markdown-доска стороннего плагина.

Начальные колонки (пользователь может менять их через корневой `_statuses.md`):
1. Backlog — `backlog`.
2. In Progress / В работе — `in-progress`.
3. Done / Завершено — `done`.

Доска автоматически выбирает все карточки `type: task` из папки задач. `groupBy.property: note.status`, groupOrder берётся из порядка строк `_statuses.md` (начально backlog/in-progress/done). Заголовки колонок соответствуют значениям status; заголовок карточки — title, ниже summary/id/tags. Пользователь вправе добавлять статусы, например review/blocked с ролью active. Агент перед работой читает реестр и не использует встроенный фиксированный список.

Точный синтаксис нативного Kanban см. в скилле obsidian, references/native-kanban.md и references/official-bases-syntax.md. Требуются Obsidian 1.14+ и включённый Bases; при более старой версии обновить приложение, а не выдавать таблицу за канбан.

## Команды
```bash
obsidian-project-framework task create "Добавить вход" --key auth-login \
  --summary "API входа и проверки авторизации" --tag модуль/auth
obsidian-project-framework task create "Интерфейс входа" --related TASK-001 --depends-on TASK-001
obsidian-project-framework task start TASK-001
obsidian-project-framework task status TASK-001 backlog
obsidian-project-framework task start TASK-001
# После отчёта и реальных проверок:
obsidian-project-framework task complete TASK-001
# После перетаскивания карточек в Obsidian:
obsidian-project-framework task sync
```

## Карточка
Имя: `TASK-001_backlog_2026-10-27.md`. Номер стабилен; статус и дата в имени меняются вместе со статусом. Дата UTC; правка описания не меняет дату статуса. Обязательные свойства: id, type, title, summary, status, status_changed, created, updated, tags, related, depends_on, sources, review. Служебные: request_key, git_baseline, knowledge_sync, report.
Теги: `задачи`, `статус/<status>` и предметные теги. related/depends_on — точные wiki-ссылки на карточки. Разделы: запрос пользователя, описание, критерии готовности, план, результат, предложения, журнал.

## Переходы и синхронизация
- Начально backlog → in-progress → done. Допустимые значения и роли определяет `_statuses.md`, а не этот пример.
- Возврат в статус с ролью backlog и повторное открытие в active допустимы. Переход между active-статусами сохраняет Git baseline; повторное открытие из done сбрасывает готовность старого отчёта.
- До старта зависимости должны иметь роль done согласно реестру. NOW хранит текущий фокус агента; наличие нескольких задач с ролью active на доске допустимо.
- CLI меняет status, дату, имя, статусный тег, ссылки в разрешённой зоне, индекс, STATE и рабочий таймлайн вместе. Документацию модулей и Решения/ не переписывает.
- Obsidian при drag-and-drop меняет только свойство status. После перетаскивания **обязательно task sync**. Команда сначала проверяет переходы, затем согласует карточки; повтор не создаёт новые события и даты.
- Для гарантированной даты изменения использовать CLI. Если перенос в Obsidian выполнен раньше запуска sync, дата синхронизации — время обнаружения изменения; не выдавать её за известное время события.
- Перед переносом в статус с ролью done подготовить отчёт через knowledge sync. Если проверки/отчёт отсутствуют, sync откажется завершать задачу: вернуть status в подходящий active-статус из реестра и закончить работу.
- Неизвестные реестру статусы будут скрыты groupOrder. init/sync/doctor должны сообщить об этом; не преобразовывать их по догадке. Пользователь может добавить определения или явно сопоставить задачи с другими значениями. Подробнее — statuses.md.

## Завершение и границы записи
Обновить результат и `_agents/Knowledge/`, приложить отчёт `_agents/Reports/` с реальными проверками. Документацию модулей, включая API, без явной просьбы не менять; предложенные правки и наличие разрешения указать в отчёте. Не маркировать непроведённые/проваленные проверки как passed.

## Идемпотентность
create возвращает прежнюю задачу по --key; без ключа — по точному названию после обрезки пробелов. Для новой одноимённой задачи нужен новый ключ. Повтор текущего статуса или уже выполненной синхронизации не переписывает даты, отчёты и журнал. Dry-run не создаёт файлы/каталоги.
